# 嵌入式自动化开发工具：完整工程实施方案

> 文档版本：v1.0\
> 状态：架构与实施计划已定义；硬件时序、CLI
> 参数和各目标芯片兼容性仍须实测\
> 目标：构建一套模块化、可扩展、与具体 AI Agent 解耦的嵌入式自动化工具

------------------------------------------------------------------------

## 1. 项目目标

开发一套以 Python
为核心的嵌入式开发自动化工具，将编译、复位、烧录、串口日志采集、通信协议测试和
AI Agent 代码修复串成可重复执行的工作流。

期望工作闭环：

1.  用户描述需要修复的 Bug 或实现的改动。
2.  AI Agent 阅读项目约束和代码，分析问题并修改代码。
3.  工具调用项目指定的 IAR 或 GCC 构建流程。
4.  构建成功后，控制 CH340 的 RTS 拉低 MCU 的 NRST。
5.  启动 STM32CubeProgrammer CLI，按经实测的时序释放
    NRST，完成连接、烧录和校验。
6.  通过 CH340 持续采集串口日志，执行协议测试和日志断言。
7.  将代码差异、构建输出、烧录结果、原始串口数据、解析日志和测试报告交给
    Agent。
8.  如果测试失败，Agent
    根据证据提出修复并重新执行，达到成功条件或最大迭代次数后停止。

本项目不是单纯的烧录脚本，也不是绑定某一款 Agent
的专用插件。它是一个可以独立运行的本地自动化工具，AI Agent
是调用工具的一种客户端。

### 1.1 第一版目标

第一版优先完成：

-   Windows 本地可运行。
-   Python CLI 命令行入口。
-   支持 IAR 与 GCC 两类构建后端。
-   支持 STM32F030、STM32F070、APM32E030 三类目标配置。
-   以 BIN 文件作为烧录产物，并为每个目标明确配置烧录地址。
-   CH340 UART 数据收发、日志采集与 RTS 复位控制。
-   STM32CubeProgrammer CLI 烧录、校验和结果记录。
-   可配置的协议测试与确定性 PASS/FAIL 判定。
-   统一工作流、失败分类、运行归档。
-   预留 Agent CLI / MCP 适配，不绑定 Codex、Claude Code
    或某个模型供应商。

### 1.2 第一版暂不做

以下功能不应成为 MVP 的前置条件：

-   GUI 桌面界面。
-   动态插件发现和复杂插件市场。
-   分布式任务调度。
-   多开发板并发执行。
-   自主修改工具自身代码。
-   未经测试的自动硬件恢复动作。
-   让大模型自行判断每个协议断言是否通过。
-   一开始就支持所有烧录器、所有芯片和所有通信接口。

先让单块目标板上的完整链路可靠运行，再扩展功能。

### 2.3 安全与可靠性边界

-   不要假定 CH340 的 RTS 输出一定是 3.3 V 或某个固定极性。
-   NRST 通常为低电平有效，但必须按实际电路确认。
-   在未确认电路前，不要让 CH340 和 ST-Link
    的两个输出同时驱动同一复位线。
-   串口 RTS/DTR 在端口打开时可能出现驱动相关的状态变化。预设 RTS
    状态能降低风险，但不能保证所有驱动都没有瞬态。
-   自动烧录失败时，应释放复位并关闭相关进程；如果硬件状态无法确认，应报告失败，不要假装已恢复。
-   不允许在构建失败时继续烧录旧 BIN。
-   不允许 Agent 无限修改、编译和烧录。
-   不允许只根据大模型的自然语言判断来决定测试 PASS/FAIL。

## 3. 总体架构

``` text
┌────────────────────────────────────────────────────────────┐
│                       AI Agent 层                           │
│      Codex / Claude Code / 其他可调用工具的 Agent           │
│  需求理解、代码修改、读取报告、分析失败、提出下一轮修复      │
└────────────────────────────┬───────────────────────────────┘
                             │ CLI（第一阶段）
                             │ MCP（后续可选）
┌────────────────────────────▼───────────────────────────────┐
│                    Workflow / 编排层                        │
│ 状态机、执行顺序、超时、重试、取消、结果归档、失败分类       │
└─────────┬───────────┬──────────┬───────────┬───────────────┘
          │           │          │           │
     BuildService FlashService SerialService TestRunner LogAnalyzer
          │           │          │           │
┌─────────▼───────────▼──────────▼───────────▼───────────────┐
│                      Core / 核心层                          │
│  统一接口、结果模型、配置加载、路径规则、运行上下文、事件    │
└────────────────────────────┬───────────────────────────────┘
                             │
┌────────────────────────────▼───────────────────────────────┐
│                     Adapters / 适配层                       │
│ IAR │ GCC │ STM32CubeProgrammer CLI │ PySerial │ CH340 RTS │
└────────────────────────────┬───────────────────────────────┘
                             │
┌────────────────────────────▼───────────────────────────────┐
│                  PC、调试器、串口板与目标 MCU                │
└────────────────────────────────────────────────────────────┘
```

### 3.1 架构原则

1.  **模块职责独立**：每个模块只负责一种主要职责。
2.  **硬件资源单一所有者**：同一个物理串口由一个 `SerialSession`
    管理，其他模块通过接口调用。
3.  **依赖倒置**：工作流依赖抽象接口，不直接耦合具体 CLI
    命令或串口实现。
4.  **配置与代码分离**：目标芯片、构建命令、烧录地址、串口号、时序放入配置。
5.  **结果结构化**：模块返回统一数据对象和错误码，而不是只输出文本。
6.  **原始证据保留**：原始串口字节、CLI 输出、构建日志和 Git diff
    均可回溯。
7.  **确定性测试优先**：协议测试通过明确断言判定，Agent 负责解释和修复。
8.  **渐进扩展**：第一版不引入不必要的复杂插件框架、消息总线或分布式架构。
9.  **Agent 无关**：底层工具不依赖某一款 Agent 的私有 API。
10. **不虚构成功**：工具只有在检测到明确成功条件后，才能返回成功。

## 5. 核心数据模型与统一接口

核心接口应先定义，再开发具体适配器。以下代码为接口示意，不是已验证的完整实现。

### 5.1 统一结果模型

``` python
from dataclasses import dataclass, field
from pathlib import Path
from typing import Any


@dataclass
class OperationResult:
    success: bool
    operation: str
    error_code: str | None = None
    message: str = ""
    duration_ms: int = 0
    log_path: Path | None = None
    data: dict[str, Any] = field(default_factory=dict)
```

构建、烧录、复位和测试都应返回可机器解析的结果。不要让上层通过搜索一段自然语言来推断成功与否。

### 5.2 BuildBackend

职责：

-   调用指定编译器或构建系统。
-   捕获 stdout/stderr、退出码和耗时。
-   确认本次构建产生了预期产物。
-   验证产物路径、大小和时间戳。
-   计算产物 SHA-256。
-   返回 `BuildResult`。

建议接口：

``` python
class BuildBackend:
    def build(self, target_config, run_context):
        # 执行构建并返回结构化结果
        raise NotImplementedError
```

IAR 适配器调用配置中的 `iarbuild` 可执行文件、工程文件和构建配置。GCC
适配器执行项目配置中的真实命令，可以是 Make、CMake、Ninja 或直接 GCC
命令。

不要假定所有 GCC 工程都使用相同的构建系统。

### 5.3 Programmer

职责：

-   检查烧录工具是否存在。
-   构造经过验证的 CLI 参数。
-   执行连接、写入、校验。
-   收集退出码、标准输出、标准错误和耗时。
-   将失败分类为工具启动失败、连接失败、烧录失败、校验失败或超时。
-   将固件路径、SHA-256、烧录地址和目标配置写入结果。

建议接口：

``` python
class Programmer:
    def connect_and_flash(self, image_path, address, target_config, run_context):
        raise NotImplementedError
```

烧录器适配器不能自行决定 CH340 的复位时序；该职责属于工作流连接策略。

### 5.4 SerialSession

职责：

-   管理唯一的串口连接。
-   配置端口号、波特率、数据位、校验位和停止位。
-   启动单一接收循环，将数据分发给日志采集和测试订阅者。
-   提供原始字节接收和发送能力。
-   提供 RTS/DTR 控制能力。
-   管理接收线程/任务的启动、停止和异常。
-   防止多个组件重复打开同一 COM 端口。

建议接口：

``` python
class SerialSession:
    def open(self): ...
    def close(self): ...
    def write(self, data: bytes): ...
    def set_rts(self, value: bool): ...
    def subscribe(self, callback): ...
```

串口数据先以原始字节保存，再按配置解码成文本。不要因为日志解码失败而丢弃原始数据。

### 5.5 ResetController

职责：

-   依赖 `SerialSession` 控制 RTS，不自行打开串口。
-   将逻辑状态 `ASSERTED` / `RELEASED` 映射为实测确认的 RTS 属性值。
-   支持保持复位、释放复位和脉冲复位。
-   支持可配置时长、超时和状态记录。
-   在异常退出时尝试释放复位，并报告释放动作是否成功。

建议接口：

``` python
class ResetController:
    def assert_reset(self): ...
    def release_reset(self): ...
    def pulse(self, duration_ms: int): ...
```

配置应使用明确的逻辑字段，例如
`asserted_rts_value`，不要将"高电平"和"RTS=True"混为一谈。后者是软件 API
状态，前者是实际引脚电平。

### 5.6 LogService 与 LogAnalyzer

`LogService` 负责采集、时间戳、原始数据归档和会话生命周期。

`LogAnalyzer` 负责：

-   关键字/正则匹配。
-   日志级别识别。
-   启动标志检测。
-   断言失败、错误码和异常片段提取。
-   将指定测试前后的一段日志关联到测试结果。
-   生成面向 Agent 的精简摘要。

Agent 摘要不能替代原始日志；报告中必须保留原始日志路径。

### 5.7 TestRunner

职责：

-   加载测试套件。
-   发送协议帧或文本命令。
-   等待响应，使用明确的超时。
-   校验帧头、长度、校验和、字段值、状态码或响应顺序。
-   返回每个测试项的 PASS/FAIL 和失败证据。
-   记录发送数据、收到的数据和对应日志时间范围。

测试判定应由可重复的代码规则完成。Agent
可以建议新增断言，但不能静默更改测试预期以制造 PASS。

### 5.8 WorkflowEngine

职责：

-   管理工作流状态机。
-   按顺序调用各服务。
-   管理超时、取消、重试和资源释放。
-   为每次运行分配 `run_id`。
-   统一归档构建、烧录、日志和测试结果。
-   向 Agent 返回稳定的 JSON 结果。

工作流不能把所有业务逻辑直接写进 CLI 入口。`cli.py`
只解析参数、加载配置并调用服务。

## 6. 配置规范

配置文件描述目标差异；代码实现通用流程。未确认的配置应使用 `TODO` 或
`unverified` 标识，不得将示例值伪装成已验证值。

### 6.1 全局配置示例

``` yaml
app:
  log_level: INFO
  runs_dir: runs
  default_timeout_s: 60

serial:
  port: COM5
  baudrate: 115200
  bytesize: 8
  parity: N
  stopbits: 1
  rtscts: false
  dsrdtr: false
  read_timeout_s: 0.1
```

COM
端口和波特率应由用户按实际环境修改。第一版可以通过命令行参数覆盖配置，但必须在运行报告中记录最终生效配置。

### 6.2 目标配置示例

``` yaml
target:
  id: stm32f030
  family: STM32
  exact_part_number: TODO_CONFIRM
  status: template

build:
  backend: iar
  project_file: "C:/path/to/project.ewp"
  configuration: Release
  command: null
  artifact: "build/firmware.bin"
  artifact_format: bin

flash:
  backend: stm32cubeprogrammer_cli
  interface: SWD
  mode: NORMAL
  reset_mode: SWrst
  address: "TODO_CONFIRM_FROM_LINKER_CONFIG"
  verify: true
  timeout_s: 60

reset:
  backend: ch340_rts
  control_line: RTS
  asserted_rts_value: TODO_MEASURE
  pulse_ms: 100
  release_delay_ms: TODO_MEASURE
  open_transient_verified: false

startup:
  ready_pattern: null
  timeout_s: 5
```

注意：

-   `address`
    必须来自对应工程的链接配置或固件布局，不允许仅凭芯片型号推断。
-   `reset_mode: SWrst` 只是 CLI 候选配置，需要按本机 CubeProgrammer
    版本和目标芯片实测。
-   `release_delay_ms` 需要从自动化连接实验得到。
-   `pulse_ms`
    用于普通复位时可独立于烧录辅助连接延时；不要把两种时序混为一个参数。
-   APM32E030 的工具支持状态必须独立记录，不能沿用 STM32 的已验证状态。

### 6.3 固件产物防错

每次构建至少记录：

-   本次构建开始时间。
-   编译器和版本（如果可获得）。
-   工程路径和构建配置。
-   命令及退出码。
-   BIN 路径、文件大小、修改时间和 SHA-256。
-   目标型号与烧录地址。
-   本次构建是否明确成功。

构建失败时，工作流不得继续使用上一次遗留的
BIN。推荐每次运行使用独立的产物目录，或在构建前清理明确指定的输出目录。

------------------------------------------------------------------------

## 7. 复位辅助烧录流程

### 7.1 人工流程基线

当前人工流程：

1.  拉住 MCU 的 RST/NRST。
2.  在 STM32CubeProgrammer GUI 中点击 Connect。
3.  等待连接过程启动。
4.  释放 RST/NRST。
5.  连接成功后烧录。

自动化要复现这套已知可工作的流程，而不是未经验证地改成另一种连接方式。

### 7.2 第一版自动化流程

建议将连接策略单独命名为 `ResetAssistedConnectStrategy`：

1.  验证构建产物存在且本次构建成功。
2.  打开 CH340，初始化串口状态。
3.  确认接收线程已经准备好（如本次运行需要捕获启动日志）。
4.  使用已验证的 RTS 属性值将 NRST 拉低。
5.  使用 `subprocess.Popen()` 启动 CLI 连接/烧录进程，使 Python
    可以继续控制复位时序。
6.  在配置的释放时机将 NRST 拉高。
7.  等待 CLI 连接、烧录和校验结束。
8.  检查进程退出码、输出内容和校验结果。
9.  记录完整日志与耗时。
10. 失败时分类、清理进程并尝试释放复位。

第一阶段可以通过可配置的短延时来模拟人工时序，但该延时必须通过实验确定。GUI
的"卡顿"不能作为自动化的同步信号。

### 7.3 必须先做 Connect-only 实验

不要一开始就将连接、写入、校验、复位全部拼成一条长命令。

先编写一个最小实验程序：

-   拉低 NRST。
-   启动 CLI 的连接操作。
-   延迟若干候选时间后释放 NRST。
-   只判断是否成功连接。
-   保存进程输出、时间戳和每次测试的参数。
-   找出稳定的时序范围。
-   再加入写入 BIN 与校验。

连接实验成功后，再测试完整烧录命令。具体 CLI 参数应以本机安装版本的
`STM32_Programmer_CLI.exe --help`、对应版本官方文档和真实输出为准。

### 7.4 连接模式

当前 GUI 使用 `Normal`，第一版优先保留该模式。`Under Reset`
不作为默认方案，因为当前 ST-Link 克隆版的 NRST 功能不可依赖。

CLI
连接模式、复位模式、目标接口和写入地址必须作为配置项，而不是散落在代码中的字符串。任何模式调整都需要针对每种目标
MCU 重新验证。

### 7.5 异常处理

-   CLI 无法启动：记录工具路径和系统错误，尝试释放 NRST。
-   连接超时：保存 CLI 输出，终止或回收子进程，释放 NRST。
-   烧录失败：不启动协议测试，保留失败证据。
-   校验失败：标记 `FLASH_VERIFY_FAILED`，禁止报告成功。
-   复位控制失败：停止后续硬件操作并标记硬件状态不确定。
-   Python 被中断：使用 `try/finally`
    清理资源；对进程中断、系统关机等无法保证执行的情况，必须在文档中说明限制。
-   不进行无限重试；默认一次失败后最多有限重试，且必须保存每次尝试记录。

------------------------------------------------------------------------

## 8. BIN 烧录地址与芯片配置

BIN 是原始字节内容，不携带自身的 Flash
起始地址。因此，每个固件配置必须显式指定地址。

地址来源优先级：

1.  IAR 链接配置。
2.  GCC linker script。
3.  项目中明确维护的固件布局文档。
4.  经负责人确认的产品配置。

禁止只凭 `STM32F030`、`STM32F070` 或 `APM32E030`
的型号自动猜测烧录地址。即使常见应用固件位于某个地址，也可能因为
Bootloader、分区或定制启动流程而不同。

烧录前至少检查：

-   目标配置与构建配置一致。
-   BIN 不是空文件。
-   BIN 路径是本次构建产物。
-   地址格式合法。
-   固件长度没有超出配置允许的区域。
-   地址与固件链接布局一致。
-   目标型号使用了正确的配置文件。

如果尚未建立 Flash
区域容量校验，必须明确标记为未实现，而不是声称工具已验证不会越界。

## 9. 串口采集与协议测试设计

### 9.1 串口数据路径

``` text
CH340 COM Port
      │
      ▼
SerialSession（唯一端口所有者）
      │
      ├── 原始字节记录器 ──> serial.bin / serial.jsonl
      │
      ├── 文本解码器 ──────> serial.log
      │
      ├── LogAnalyzer ─────> 错误摘要
      │
      └── TestRunner ──────> 协议响应与断言
```

同一串口只允许一个组件直接读取数据。日志采集和测试通过订阅同一数据流协作，避免两个线程分别从
COM 端口读取而抢走数据。

### 9.2 原始日志与解码日志

建议同时保存：

-   `serial.bin`：原始字节流。
-   `serial.log`：带时间戳的解码文本（如果文本解码适用）。
-   `serial.jsonl`：可选的事件记录，每条包含时间戳、方向、数据和来源。
-   `test_report.json`：测试结果与关联日志范围。

若协议是二进制协议，不应把文本解码作为唯一证据。

### 9.3 协议测试用例

每个测试用例应描述：

-   测试名称。
-   前置条件。
-   发送数据（文本或十六进制）。
-   期望响应或响应匹配规则。
-   超时。
-   校验逻辑。
-   PASS/FAIL 条件。
-   失败时需要保留的日志窗口。

测试框架必须支持可重复执行。对于具有副作用的命令，需明确测试前置状态和恢复方式。

### 9.4 启动日志捕获

推荐顺序：

1.  确认串口接收循环已启动。
2.  开始本次运行的日志归档。
3.  释放 NRST。
4.  等待启动标志或启动超时。
5.  进入协议测试。

这样可减少错过启动日志的概率。若启动标志未知，第一版可以使用配置化延时，但应将其标记为较弱的启动判定方式。

## 10. 工作流状态机

推荐的状态机：

``` text
IDLE
  │
  ▼
VALIDATE_CONFIG
  │
  ▼
BUILD
  ├── failure ──> BUILD_FAILED ──> ARCHIVE
  │
  ▼
VALIDATE_ARTIFACT
  ├── failure ──> ARTIFACT_FAILED ──> ARCHIVE
  │
  ▼
OPEN_SERIAL
  ├── failure ──> SERIAL_OPEN_FAILED ──> CLEANUP
  │
  ▼
ASSERT_RESET
  │
  ▼
START_PROGRAMMER
  │
  ▼
RELEASE_RESET_AT_CONFIGURED_TIME
  │
  ▼
WAIT_FLASH_AND_VERIFY
  ├── failure ──> FLASH_FAILED ──> CLEANUP
  │
  ▼
START_LOG_CAPTURE / WAIT_BOOT
  │
  ▼
RUN_TESTS
  ├── failure ──> TEST_FAILED ──> ARCHIVE
  │
  ▼
PASS
  │
  ▼
ARCHIVE
  │
  ▼
CLEANUP
```

若需要在烧录过程中捕获日志，串口采集应在复位释放之前就准备好。实际运行顺序需按具体测试需求确定，不能让日志监听和烧录流程互相关闭对方的串口会话。

### 10.1 清理原则

-   每条执行路径都必须进入清理阶段。
-   关闭串口前先停止接收循环并保存缓冲数据。
-   复位线最终状态要有记录。
-   所有启动的子进程都必须被等待、终止或明确报告仍在运行。
-   清理失败应附加到原始错误，不应覆盖原始失败原因。

## 11. AI Agent 集成方案

### 11.1 先 CLI，后 MCP

第一阶段提供稳定的命令行接口。能够执行命令的 Agent 可以直接调用
CLI，并读取 JSON 结果。

第二阶段可增加 MCP Server，将 CLI 的稳定能力包装为工具。MCP
层应是薄适配器，不复制烧录、串口或工作流业务逻辑。

推荐工具名称：

-   `inspect_target`
-   `build_firmware`
-   `flash_firmware`
-   `reset_target`
-   `capture_serial`
-   `run_protocol_tests`
-   `get_run_report`
-   `run_workflow`

所有工具应有明确参数、超时、结果 schema 和错误码。

### 11.2 Agent 自动修复循环

建议的循环：

1.  Agent 收到用户需求。
2.  读取项目说明、目标配置和相关代码。
3.  生成修改并检查 Git diff。
4.  调用 `build_firmware`。
5.  构建成功后调用烧录与测试工作流。
6.  读取结构化测试报告及相关原始日志。
7.  判断是否有足够证据支持修复方向。
8.  进行下一轮修改，或停止并向用户报告。
9.  成功后汇总变更、测试证据和剩余风险。

### 11.3 防止 Agent 破坏项目

-   每轮修改前保存 Git 状态与 diff。
-   建议在独立分支或 Git worktree 中执行 Agent 任务。
-   每个任务默认最多自动修复 3 轮，可配置但不应无限。
-   不能为了通过测试而静默修改测试预期。
-   不能删除失败日志或覆盖历史运行结果。
-   不得自动修改工具自身的安全限制、最大迭代次数和目标白名单。
-   发现构建环境或硬件异常时，停止代码修复循环，避免把环境故障误当作固件
    Bug。
-   如果修改涉及 Bootloader、Flash
    布局、时钟、低功耗、DMA、中断或启动代码，应在报告中突出标记。
-   Agent
    的代码修改与硬件动作分开授权；第一版可以允许自动构建和烧录，但应明确当前任务的目标板、固件和最大重试次数。

### 11.4 失败分类

建议使用固定错误码，例如：

-   `CONFIG_INVALID`
-   `BUILD_TOOL_NOT_FOUND`
-   `BUILD_FAILED`
-   `ARTIFACT_MISSING`
-   `ARTIFACT_STALE`
-   `FLASH_TOOL_NOT_FOUND`
-   `CONNECT_TIMEOUT`
-   `FLASH_FAILED`
-   `FLASH_VERIFY_FAILED`
-   `RESET_CONTROL_FAILED`
-   `SERIAL_OPEN_FAILED`
-   `BOOT_TIMEOUT`
-   `PROTOCOL_TEST_FAILED`
-   `WORKFLOW_TIMEOUT`
-   `CLEANUP_FAILED`

Agent
根据错误码、日志和上下文决定下一步，不要把所有失败都交给它自由猜测。

## 12. CLI 命令设计

以下是计划中的命令接口，具体参数名称可在实现时微调。

``` powershell
# 检查工具、串口和目标配置
embedded-auto device check --target stm32f030

# 构建固件
embedded-auto build --target stm32f030 --backend iar

# 仅烧录已指定的产物（仅用于调试；默认仍应检查产物身份）
embedded-auto flash --target stm32f030 --artifact "build/firmware.bin"

# 手动复位
embedded-auto reset --target stm32f030

# 采集串口日志
embedded-auto monitor --target stm32f030 --duration 30

# 执行协议测试
embedded-auto test --target stm32f030 --suite example_protocol

# 执行编译、烧录、启动与测试
embedded-auto run --target stm32f030 --suite example_protocol

# 仅生成本次运行报告
embedded-auto report --run-id <run_id>
```

CLI 应支持：

-   `--json`：将结果输出为机器可读 JSON。
-   `--timeout`：覆盖默认超时。
-   `--config`：指定配置文件。
-   `--dry-run`：显示计划执行的命令和步骤，不实际操作硬件。
-   `--verbose`：输出更多调试信息。

命令行参数、日志和错误信息中不得输出密钥或不必要的敏感环境变量。

### 12.1 命令返回规范

-   进程退出码 `0` 表示该命令按定义成功。
-   非零退出码表示失败。
-   JSON 输出包含
    `success`、`operation`、`error_code`、`message`、`run_id`、`log_path`。
-   运行中间状态可以写入事件日志，但最终结果必须明确。
-   终端输出仅用于阅读，Agent 应优先读取 JSON 结果和报告文件。

## 13. 运行记录与结果归档

每次运行生成唯一 `run_id`，建议目录结构：

``` text
runs/
└── 2026-10-21T103000Z_stm32f030_abc123/
    ├── run_config.yaml
    ├── run_summary.json
    ├── events.jsonl
    ├── build.log
    ├── build_result.json
    ├── flash.log
    ├── flash_result.json
    ├── serial.bin
    ├── serial.log
    ├── test_report.json
    ├── agent_summary.md
    └── git_diff.patch
```

建议归档字段：

-   运行 ID、开始和结束时间。
-   目标型号和配置文件版本。
-   当前 Git commit、工作区是否干净。
-   Agent 名称/类型（如可获得）、任务摘要。
-   构建命令、退出码、日志和固件 SHA-256。
-   烧录工具版本、命令参数、地址、连接/校验结果。
-   串口参数、复位参数和实际采用的时序。
-   测试套件版本、逐项结果和失败证据。
-   Agent 修改轮数、每轮 diff、最终停止原因。
-   清理动作和清理失败。

归档结果应不可被下一次运行覆盖。可以定期清理旧运行数据，但不应在没有明确策略的情况下自动删除失败证据。

## 14. 测试策略

### 14.1 单元测试

无需真实硬件，使用 Mock/Fake 验证：

-   配置加载和字段校验。
-   IAR/GCC 命令构造。
-   BIN 文件存在性、大小和哈希检查。
-   错误码映射。
-   工作流状态迁移。
-   超时与取消逻辑。
-   日志匹配规则。
-   协议断言。
-   Agent 最大迭代次数。
-   失败时的资源清理路径。

### 14.2 集成测试

使用真实工具但尽量减少硬件风险：

-   IAR 命令行构建一次已知工程。
-   GCC 构建一次已知工程。
-   检查 BIN 产物与构建结果。
-   执行 CLI 连接测试。
-   执行单次烧录和校验。
-   采集一段串口日志。
-   运行一条确定性协议测试。
-   验证报告和归档完整。

### 14.3 硬件测试

硬件测试需要明确记录板卡、芯片、工具版本和接线。

建议验收：

1.  RTS 两种软件状态对应的 NRST 电平已测量。
2.  打开、关闭串口不会产生不可接受的复位瞬态，或已采用硬件措施规避。
3.  连续复位后 MCU 能正常启动。
4.  启动日志捕获稳定。
5.  连接辅助复位流程成功。
6.  BIN 烧录与校验成功。
7.  失败时 NRST 不会被软件永久保持在复位状态。
8.  连续自动烧录 20 次无人工干预通过。
9.  IAR 和 GCC 两条构建路径分别验收。
10. 三种目标 MCU
    分别记录支持状态，不以一个目标的成功推断另外两个目标成功。

### 14.4 Agent 闭环测试

先使用一个容易复现的已知 Bug：

-   测试失败时能够提取确定的失败证据。
-   Agent 只修改相关代码，不进行无关重构。
-   构建失败时不烧录。
-   烧录失败时不运行协议测试。
-   测试通过后停止继续修改。
-   超过最大轮数后停止并汇报，而不是无限循环。
-   每轮的修改、构建、烧录和测试结果可追溯。

## 15. 开发阶段与交付物

### 阶段 0：硬件和环境核验

交付物：

-   `HARDWARE_SETUP.md`
-   CH340 RTS/NRST 极性和电平记录。
-   ST-Link 与 NRST 接线确认。
-   本机 STM32CubeProgrammer CLI 版本与帮助输出。
-   CLI 连接时序实验记录。
-   三种目标的准确芯片型号、固件地址来源。
-   IAR/GCC 工程构建命令与产物路径。

完成标准：所有影响烧录安全的未知项都有明确的实测结论，或者被标记为阻塞项。

### 阶段 1：核心骨架与 CLI

交付物：

-   Python 包结构。
-   配置加载器。
-   统一数据模型和错误码。
-   `--help`、`--json`、`--dry-run`。
-   单元测试。

完成标准：不连接硬件也能测试配置、结果模型、工作流状态和错误处理。

### 阶段 2：串口和复位

交付物：

-   `SerialSession`。
-   原始日志采集。
-   RTS 控制。
-   `ResetController`。
-   `device check`、`reset`、`monitor` 命令。

完成标准：串口只由一个组件管理；复位极性已验证；能稳定采集启动日志。

### 阶段 3：构建和烧录

交付物：

-   IAR BuildBackend。
-   GCC BuildBackend。
-   STM32CubeProgrammer CLI 适配器。
-   BIN 产物校验。
-   连接辅助复位策略。
-   烧录结果和校验报告。

完成标准：先在一个已知可工作的 STM32
目标上完成连续烧录验收，再逐个扩展目标。

### 阶段 4：日志与协议测试

交付物：

-   LogAnalyzer。
-   TestRunner。
-   示例协议测试套件。
-   结构化测试报告。

完成标准：可以自动识别至少一类已知错误，并给出确定的 PASS/FAIL
结果及相关日志。

### 阶段 5：完整工作流

交付物：

-   WorkflowEngine。
-   状态机与清理逻辑。
-   `run` 命令。
-   每次运行的独立归档。

完成标准：一条命令完成构建、烧录、启动、测试和报告归档。

### 阶段 6：AI Agent 接入

交付物：

-   Agent 工具使用说明。
-   修复循环策略。
-   最大迭代次数和停止条件。
-   变更 diff 和运行证据关联。
-   可选 MCP Server。

完成标准：Agent 能依据真实测试结果修复一个已知
Bug；成功时停止，失败达到上限时明确汇报。

### 阶段 7：扩展与稳定性

交付物：

-   STM32F030、STM32F070、APM32E030 的逐项兼容性记录。
-   IAR/GCC 与目标型号的支持矩阵。

## 18. 实施原则与最终结论

### 18.1 必须坚持的原则

1.  先验证硬件和工具时序，再实现自动化。
2.  先完成独立模块，再组合工作流。
3.  先使用 CLI，后添加 MCP。
4.  先做确定性协议测试，再做 Agent 自动修复。
5.  先在一个 STM32 目标上跑通，再扩展至其余目标。
6.  所有成功结论必须来自真实退出码、校验结果或测试断言。
7.  所有失败都应保留证据。
8.  每次 Agent 修复都应可回滚、可追踪。
9.  不为尚未出现的需求过度设计。
10. 不将未验证的示例参数视为生产配置。

### 18.2 当前方案的完成度

当前已明确：

-   整体架构和模块边界。
-   IAR/GCC 双构建后端设计。
-   BIN 固件的地址管理要求。
-   CH340 RTS 控制 NRST 的复位控制器设计。
-   ST-Link CLI 烧录适配器的职责。
-   日志采集、协议测试和工作流状态机。
-   与具体 AI Agent 解耦的 CLI-first、MCP-later 接入路线。
-   分阶段开发和验收标准。

当前尚未通过实测：

-   RTS 的电气极性、电平与串口打开瞬态。
-   CLI 连接辅助复位的最佳时序。
-   本机 CubeProgrammer CLI 的具体参数组合。
-   三种 MCU 的确切固件地址和完整兼容性。
-   真实 IAR/GCC 工程的构建命令与产物路径。
-   端到端自动烧录与 Agent 修复闭环。

**结论：这份文档足以作为工程实施计划和交给 AI Agent
的开发基线，但不代表软件已经实现或硬件流程已经验证。开发过程中应按阶段验收，不应跳过硬件时序和烧录地址核验。**
